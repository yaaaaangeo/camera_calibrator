# 카메라·LiDAR 캘리브레이션 (멀티 타겟 · 멀티 카메라) — 상세

보드 여러 개가 서 있는 방에서 **한 번 캡처한 데이터**로 LiDAR 와 **여러 카메라**의 extrinsic 을 한꺼번에 구한다.
보통은 메인 앱(`./run.sh`) 홈 화면의 **CAMERA–LiDAR** 로 연다. 배치 실행은 저장소 루트에서:

```bash
./cli.sh camera-lidar <bag|폴더> --vehicle 차량 --lidar T1[,T2] \
    --cameras /cam/a=FRONT_LEFT,/cam/b=FRONT_RIGHT [--roi x0,x1,y0,y1,z0,z1[,yaw]] [--sweeps 1]   # CLI
./run.sh   # GUI: 홈에서 차량을 고르고 CAMERA–LiDAR
```

Camera Intrinsic 과 같이 쓰는 부분은 `intrinsic/shared/` 에 있다: 실시간 수신(ROS 1 직접 / rclpy /
DDS), bag 읽기·메시지 디코딩, 카메라 모델 연산(`camera_ops`), 렌즈 프리셋 읽기·쓰기, ArUco 검출 설정.

**카메라마다 푸는 순서**: LiDAR 자동 탐색은 보드 일부만 찾는 경우가 많고, 나머지는 먼저 푼 카메라의
extrinsic 으로 "배치"된다. 그래서 보드가 많이 보이는 카메라부터 풀고, 보드 3쌍 이상으로 믿을 만하게
풀린 카메라만 보드를 배치한다 (보드 1개로 틀리게 풀린 카메라가 엉뚱한 보드를 만들어 다른 카메라를
망치지 않게). 그 뒤 보드 풀이 늘었으면 3쌍 미만이던 카메라를 한 번 더 푼다.

## 결과 폴더 — 차량 / 캡처 날짜 / 카메라

```
extrinsic/calib_result/
  <차량>/
    vehicle.yaml                  차량 프로필: LiDAR 토픽, 카메라 토픽→이름·프리셋, ROI, 보드 규격
    2026-11-18_143205/            세션 = 캡처 1회. 이름은 캡처 시각 (bag 이면 녹화 시각)
      session.yaml                언제·무엇으로·카메라별 결과 요약 (+ 메모)
      capture/                    캡처 원본 (rosbag2 mcap) — 오프라인 재현용
      FRONT_LEFT/                 카메라마다
        extrinsic.txt  result.yaml  boards.yaml  overlay.png  report.txt
```

- 시작하면 차량을 고른다(새 이름이면 새 차량). 지난 세션 목록과 카메라별 px 가 보인다.
- 같은 차량을 다시 하면 프로필에서 **LiDAR 토픽, 카메라 이름, 내부 파라미터 프리셋, ROI** 가 그대로 들어오고,
  지난 세션의 결과가 카메라 이름으로 짝지어져 **기존 extrinsic** 으로 걸린다 (라이브 화면 비교 + 매칭 힌트).
- `result.yaml` 머리에 차량·세션·날짜·카메라 이름·토픽이 들어간다.

## 단계

1. **캡처** — 실시간 탭(기본) 또는 bag 탭
2. **LiDAR 보드** — BEV(위에서 본 화면)에 ROI 를 그리면 그 안에서만 자동 탐색. 모든 카메라가 같이 쓴다
3. **카메라** — `모든 카메라 자동 순위` 로 카메라마다 내부 파라미터 프리셋을 보드 재투영 오차로 고른다
4. **카메라 보드** — `모든 카메라 보드 검출`
5. **대응·풀이** — `모든 카메라 풀기`. 위 표가 카메라별 요약, 아래가 선택한 카메라의 보드별 수치
6. **오버레이 검증** — 상단 `카메라` 선택으로 카메라를 바꿔 가며 확인
7. **저장** — 체크한 카메라를 모두 세션 폴더에, `session.yaml` 과 차량 프로필 갱신

3~6 단계는 카메라마다 하는 단계라, 창 위쪽에 **카메라 선택**이 나온다.

## 실시간 캡처

1. `탐색` → 토픽 표에서 LiDAR(여러 개 = 합침)와 카메라(여러 개)를 체크하고 `구독 시작`
2. 오른쪽 위에 **구독 중인 모든 카메라가 썸네일로** 뜬다. 썸네일에는 ArUco 마커 검출 수가 표시된다
   - 토픽 이름으로는 위치를 모를 때가 많으니, 그림을 보고 보드가 보이는 카메라를 `포함` 하고 이름(`FRONT_LEFT` 등)을 붙인다
   - `마커 보이는 카메라만 포함` 버튼으로 한 번에 고를 수 있다
   - 썸네일을 클릭하면 아래에 크게 보인다: 영상 / 마커 / 보드 검출 / **점 투영**(기존 extrinsic 또는 이번 결과, 번갈아 보기)
3. `캡처` — 기본은 **LiDAR 1스윕 + 카메라마다 1장** (LiDAR 시각에 가장 가까운 프레임). 스윕·프레임 수는 늘릴 수 있다
4. 캡처가 세션 폴더의 `capture/` 에 mcap 으로 저장되어, 나중에 bag 탭으로 열면 같은 결과가 재현된다

경고가 뜨는 경우: 최근 스윕끼리 5 cm 안에서 겹치는 비율이 85% 아래(차량·보드가 움직임), 카메라와 LiDAR 시각차 200 ms 초과.

## ROI

- BEV 에서 `드래그로 ROI 그리기` → 드래그. 모서리·변 핸들로 크기, 위쪽 원 핸들로 회전. 높이(z)는 숫자로
- 여러 개 가능 (정면 벽, 좌측 벽 …). 없으면 전체 클라우드를 탐색한다 (느림)
- 탐색이 끝나면 ROI 는 차량 프로필에 저장되고, 다음 세션은 LiDAR 단계에 들어가자마자 자동 탐색한다
- 보드가 ROI 경계에 걸려도 검출기는 ROI 밖 0.4 m 까지 본다 (`ROI_MARGIN`)

측정 (Hesai 128ch, 1스윕, 보드 6개 모두 검출, 결과 동일):

| 데이터 | 전체 탐색 | ROI |
|---|---|---|
| 11-05 16_41_00 | 19.7 s | 1.6 s |
| 11-05 16_38_15 (카메라 3대) | 16.5 s | 1.6 s |
| 11-03 merge 2토픽 | 6.5 s | 0.7 s |

## 카메라 방향 — 보드가 1~2개만 보이는 카메라

보드가 모두 똑같아서(마커 ID 동일) 보드 **1개**만 보이는 카메라는 그 보드가 LiDAR 의 어느 보드인지 보드만으로는 알 수 없습니다.
어느 LiDAR 보드에 맞춰도 오차 0 으로 똑같이 맞기 때문입니다. 그래서 두 가지로 가립니다.

1. **빔 통과 검사 (자동)**: 후보 대응이 카메라를 놓는 자리에 LiDAR 빔이 지나가면(1스윕에서 반경 15 cm 안 20개 초과) 버립니다.
   잘못된 대응은 카메라를 차량 밖 허공에 놓기 때문에 대부분 여기서 걸러집니다.
   단, 빔이 카메라 근처를 스쳐 지나가는 자리(예: rear)에서는 정답도 걸릴 수 있어서, 빔 통과 **만으로** 버려진 대응이
   통과한 후보보다 보드를 2개 이상 더(최소 3개) 보드당 8 cm 안으로 맞추고 방향도 맞으면 되살립니다
   (결과 노트: `빔통과 검사에 걸린 대응을 되살렸습니다 …`).
2. **카메라 방향 (사람이 지정)**: 정면 / 좌전 / 좌 / 좌후 / 후 / 우후 / 우 / 우전. 차량 정면 기준 ±50° 안을 보는 대응만 남깁니다.
   - 라이브 썸네일의 이름 옆, bag 탭 카메라 표, 5단계 개요 표에서 고릅니다. 5단계에서 바꾸면 그 카메라를 바로 다시 풉니다
   - 이름·토픽에 front / left / right / rear 가 있으면 자동으로 들어갑니다 (`cam4` 같은 이름은 직접 골라야 합니다)
   - 차량 프로필(`vehicle.yaml`)에 저장되어 다음 세션에 그대로 쓰이고, Git 업로드로 다른 PC 에도 넘어갑니다
   - CLI: `--cameras /cam/a=cam4:좌,/cam/b=cam7:우`

차량 정면은 **보드 3개 이상 보이는 카메라 중 방향이 있는 것**(보통 정면 카메라)이 정합니다. 그래서 풀이 순서는 보드 많은 카메라 먼저,
1~2개짜리가 나중입니다. 정한 정면은 프로필에 `forward_deg` 로 저장되어, 다음에 그런 카메라가 없을 때 대신 쓰입니다.

디버깅 bag(`cal_room_debugging`): left / right / cam4 / cam7 모두 보드 1개. 빔 통과 검사 + 방향(cam4 좌, cam7 우)으로
left·cam4 = 좌측 보드, right·cam7 = 우측 보드, left [+0.93, −1.70] / right [−0.94, −1.79] 로 좌우 대칭이 됩니다.
방향이 없으면 `모호 — 방향 지정` 으로 표시합니다.

**그래도 정밀도는 보드 수가 정합니다.** 보드 1개(구멍 간격 50 × 40 cm)는 구멍 중심 오차 몇 mm 로도 회전이 1° 가까이 흔들립니다.
측면·후방 카메라에도 **거리·높이가 다른 보드 2~3개**가 보이게 배치하는 것을 권합니다.

## 보드 여러 장을 한 프레임에 세운 구조물

보드를 위아래로 붙여 세운 구조물(예: 3단)은 보드끼리 거의 같은 평면이라 평면 찾기에서 **한 장짜리 큰 평면**으로 합쳐집니다.
그래서 보드 크기보다 큰 평면(긴 변이 보드 3.5장까지)은 **보드 크기 창으로 나눠서, 창마다 평면을 다시 맞춘 뒤** 구멍을 찾습니다.

- 창에서는 모델 정합(구멍이 안 보일 때 보드 도면 전체를 맞추는 것)을, 같은 평면에서 **구멍으로 확인된 보드가 하나 이상 있을 때만** 씁니다.
  맨 벽에서 보드 비슷한 자리를 잡는 것을 막기 위해서입니다. 바닥에 걸려 잘린 맨 아래 보드는 이렇게 잡힙니다
- 구멍 4개는 **보드의 구멍 직사각형(0.5 × 0.4 m)과 15% 안으로 맞아야** 보드로 인정합니다. 체커보드의 검은 칸처럼 점이 덜 맺히는 곳이
  구멍 4개로 잡히는 것을 거릅니다 (실제 보드 0~8%, 가짜 25% 이상)

## LiDAR 기종 (벨로다인)

보드 탐지는 128채널과 같은 코드다. 구멍 검출이 실패하면 보드 도면 전체를 점에 맞추는 template 정합이 대신 잡는다.
벨로다인용으로 바뀐 점:

- **줄 간격을 점마다** 잰다 (`local_line_gap`). VLP-32C 는 지평선 근처 채널이 0.33°, 몇 도 아래는 1~2.5° 간격이라
  한 보드 안에서도 위는 줄 간격 3 cm, 아래는 10~23 cm 다
- 구멍 둘레 검사에서 **줄 사이 빈틈**(위아래 양쪽에 패널 점이 있는 곳)은 패널로 본다. 보드 가장자리 밖은 여전히 걸러진다

합성 룸(보드 6개 × 배치 3가지, 1스윕) 검출 수 / 18 (개발 중 측정값):

| LiDAR | 이전 | 지금 |
|---|---|---|
| VLP-32C | 8 | 10 |
| HDL-32E | 2 | 9 |
| VLP-16 | 0 | 5 |
| 128채널 | 17 | 17 |

**VLP-32C 보드 배치 주의**: 놓친 보드는 대부분 센서보다 높이 달린 보드(+6°)다. VLP-32C 의 +4.7° 위 채널은
2.3~3.3° 간격이라 7 m 에서 줄 사이가 30~40 cm — 보드에 2~3줄밖에 안 걸려 어떤 검출기로도 못 찾는다.
벨로다인 차량에서는 **보드 중심을 센서 높이 ±2 m 안(지평선 −4°~+2° 부근)** 에 두면 줄이 촘촘하게 걸린다.

## 다운샘플된 점군 (복셀 필터를 거친 토픽)

녹화 전에 복셀 다운샘플된 점군(예: PV5 `merge/ground_points`, 1스윕 표본 간격 10~11 cm, ring 없음)은
보드 구멍(지름 24 cm)이 표본 1~2개 빈자리로만 보여 구멍 검출로는 찾을 수 없다. 1스윕의 점 간격이
`SPARSE_SPACING`(6 cm) 이상이면 **성긴 모드**로 바뀐다:

- 평면 패치를 표본 간격 크기 복셀로 찾는다 (더 잘게 하면 쌓인 스윕이 보드를 조각냄: 패치 280개 22 s → 155개 0.4 s)
- 보드는 template 정합으로 찾고, 구멍 판정은 "패널이었으면 들어갔을 점 수" 대비 비율로 한다
  (구멍마다 50%, 4개 합 25% 이하). 3단 스택의 창(window)에도 template 을 쓴다 (구멍으로 증명될 일이 없으므로)
- **벽 위의 무늬를 거른다**: 패널 바깥 띠(좌·우·위·아래) 중 1면 이상이 비어 있어야 보드. 벽은 사방이 차 있다
- 좌우(또는 위아래) 양쪽이 비어 있으면 패널 가장자리로 중심을 다시 잡는다 (구멍만으로는 표본 격자 단위로 양자화됨)
- 스윕 수 `자동`(기본)이면 10스윕을 쌓는다. 복셀 평균은 스윕마다 조금씩 달라서 쌓으면 표본이 실제로 늘어난다

bag 을 열 때는 **차량·보드가 정지한 구간**을 자동으로 고른다 (`still_moment`). 요청한 시점(기본 가운데)이
움직이는 중이면 가장 긴 정지 구간의 가운데로 옮기고 그렇게 했다고 알린다.
`PG_PV5_01_cal.bag` 은 0~16 s 만 정지, 이후 주행이라 가운데(30 s)를 쓰면 보드가 번져 결과가 시점마다 달랐다.

측정 (PV5 bag 2개, 이전 → 지금):

| bag | 이전 | 지금 |
|---|---|---|
| PG_PV5_01_cal (front_wide·narrow) | LiDAR 보드 0개, 두 카메라 모두 실패 | 보드 9개, 카메라마다 8쌍, 10 s |
| PV5_01_10-38-42 (top·bottom_center) | 보드 3개, 3쌍·4쌍 | 보드 10개, 6쌍·9쌍, 시점 3곳 결과 차이 ±2 cm·±0.2° (top) |

남는 오차는 대부분 카메라 쪽이다. PV5 카메라용 렌즈 프리셋이 없어 범용 `31CAM_*` 이 골라지고, front_wide 는
앞유리 뒤라 10 m 보드의 깊이가 10~20 cm 틀린다 — CAMERA INTRINSIC 으로 장착 상태 그대로 렌즈를 잡아 등록할 것.

## 알아둘 것

- **다른 PC 에서 ROS 2 클라우드를 받을 때**: `net.core.rmem_max` 가 작으면(기본 208 KiB) 큰 클라우드 조각이 버려진다.
  `sudo sysctl -w net.core.rmem_max=8388608` 권장. 탐색 결과에 경고로 나온다.
- **ROS 1 실시간**: rospy/rosmaster 1.15(Noetic)로 탐색·Image·CompressedImage·PointCloud2 수신, 늦게 뜬 퍼블리셔,
  재시작한 퍼블리셔, 스냅샷 mcap 재생까지 확인했다. 로봇 PC 의 master 에 붙을 때는 master 칸에 `http://<로봇 IP>:11311`.
  토픽은 보이는데 데이터가 안 오면 사유가 화면에 나온다 — 대부분 로봇 PC 가 자기 호스트명으로 광고해서 이 PC 가 그 이름을
  못 찾는 경우다(로봇 PC 에서 `export ROS_IP=<로봇 IP>` 후 노드 재시작, 또는 이 PC 의 `/etc/hosts` 에 추가).
  이 PC 의 주소는 master 로 가는 네트워크 카드의 IP 를 자동으로 쓴다(`ROS_IP`/`ROS_HOSTNAME` 이 있으면 그것).
- 캡처 mcap 은 metadata version 8 로 쓴다. Humble 의 `ros2 bag` 이 version 9 를 못 읽기 때문.
- 이 리그의 `merge` 토픽은 지면 분리기가 2 m 위를 `ground_points` 로 보내므로 **두 토픽을 모두** 골라야 높이 달린 보드까지 보인다.
